## M1 — lane schema (additive, version stays 1)
Optional `lane` object on Recipe, in BOTH shared/recipe.schema.json and the
recipes.js validator, and as an optional TS field in shared/types.ts:
  lane: { "pool": string, "order": number } | null
Validator rules: only kind "llm" recipes may carry lane (else field ignored
with a warning string in loadRecipes result, not an error — old files stay
valid); pool pattern ^[a-z0-9][a-z0-9-]{0,31}$; order integer >= 0.
Tests: extend agent/catalog/__tests__ media/recipes patterns + new cases
(valid lane, non-llm ignored, bad pool rejected-or-warned per style you find
in recipes.js — follow its existing warn-vs-error split).

## M2 — deriveLanes + GET /lanes
NEW `agent/catalog/lanes.js`: `deriveLanes({ listRecipes, containers, versions })`
(pure; takes arrays, no fs):
  -> { pools: [ { id, lanes: [ { recipe: name, modelId, port, order, running,
       containerName, state } ] } ],
       candidates: [ { containerName, image, ports[], reason } ] }
Lane state: running when a live version/container matches the recipe's port/
containerName. Candidates: containers NOT matching any lane recipe whose name
matches /^(lane|lanes|vllm|sglang|llama?)[-_]/ OR whose exposed ports match a
lane-recipe port — advisory only, never actionable (a candidate is not a
service). Pools sorted by id, lanes by order.
Wire: agent/telemetry.js snapshot gains `lanes` (call deriveLanes with
containers from docker collector — where telemetry already sources services/
docker; if the placeholder means no container source yet, thread
listContainers through telemetry's existing deps the same way versions gets
its inputs; if genuinely impossible in the snapshot path, export a collector
hook the http layer uses and say so in the report). NEW GET /lanes in
agent/http.js (same bearer auth + JSON as /versions; 503-safe shape).
Agent tests: lanes.test.js (pure fn: pools/lanes/candidates cases, ordering,
non-llm lane ignored) + http GET /lanes auth + shape test in http.test.js
pattern.
